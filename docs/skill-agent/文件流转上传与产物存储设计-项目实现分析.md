# 《AI Agent 里的文件流转:上传与产物存储的完整设计》分析与项目实现对比报告

- **日期**: 2026-09-04
- **分析对象**: `docs/skill-agent/AI-Agent里的文件流转上传与产物存储的完整设计.md`
- **对比基线**: BookForge 项目实际实现（pi-coding-agent 0.84.2，RPC 模式）
- **适用范围**: 开发人员（后端 `backend-ts` / 前端 `frontend`）
- **结论先行**: 设计文档的核心原则合理，且与 pi 的实际架构高度一致；项目实现已落地文档推荐的主要做法（差分产物检测、大文件走工具、路径白名单）。真正值得做的优化有两项：① 水合时把 manifest 检测到的产物绑定到消息卡片（补上「shell 写文件被漏」的展示缺口）；② 去掉每轮双次同步工作区遍历。**两项已于 2026-09-04 实施完成（见第七章）**。对象存储 + file_id + DB 是「横向扩展时才需要」的触发器，不是当前单机部署的缺陷。

## 一、设计文档本身是否合理

### 1.1 合理且与 pi 架构一致的部分

- **核心主线「文件本体永远存放在上下文之外，对话里流动的只是引用，需要时按引用取回」** —— 这正是 pi 的模型（工作区落盘 + `read`/`grep`/`bash` 工具按需读取），原则正确。
- **产物检测推荐方案 (c)「约定目录 + diff 检测」** —— 正确，它是唯一能捕获 shell 命令写入文件的方式，不依赖模型自觉。
- **安全红线**（worker 侧执行 I/O、basename/路径白名单、大文件不整块回灌、HTML 渲染用成熟库消毒）—— 全部合理。

### 1.2 有条件成立、并非普适的部分

| 文档断言 | 适用前提 | 本项目现状 |
| --- | --- | --- |
| §2.3「分布式平台必须用对象存储 + file_id + 入库」 | 多 worker / 横向扩展 / 沙箱临时回收 | 单机部署，本地磁盘寻址完全够用 |
| §3.2 目录树 + 懒加载 + 虚拟滚动 | 整个项目（成百上千文件）的工作区 | 素材生成平台，每工作区文件很少，扁平列表即可 |
| §3.3 大文本分页 / 媒体 Range 端点 | 工作区出现几十 MB 日志 | 目前产物为小文件，流式整发即可 |

> 结论：文档是一份面向「通用 Agent 平台 / 代码生成平台」的架构蓝图，其中关于分布式存储、目录树、渲染矩阵的部分对当前部署属于过度设计，但对将来扩展有明确的指导价值。

## 二、pi-agent 的实现方式（对照文档）

> 代码基线：`docs/skill-agent/pi-main/packages/coding-agent/src`（与安装的 `@earendil-works/pi-coding-agent@0.84.2` 一致）

### 2.1 上传 → 递给模型

| 文档类型 | pi 实现 | 与文档对照 |
| --- | --- | --- |
| 图片 | `@file` CLI（`cli/file-processor.ts`）→ base64 `ImageContent` 块，自动缩放至 2000×2000（`processImage`）；RPC 模式经 prompt 命令 `images` 字段直传 | 匹配「图片多模态块」的 base64 变体；文档更推崇 URL/file_id 引用（见 §4.4 限制） |
| 小文本 | `@file` CLI → 以 `<file name="…">…</file>` 块**拼进 user 消息** | 匹配「小文本注入 user 消息」；项目侧没有文本上传，不适用 |
| 大文件 | 工作区落盘 + `read`（`core/tools/read.ts`，offset/limit 分页、行/字节双截断 + `Use offset=N to continue` 提示）+ `grep`/`find`/`ls`/`bash` | **完全匹配** §1.6「给路径 + 给工具，模型多轮读取」 |
| 上下文文件 | `--no-context-files` 关闭自动发现；项目改用 `--append-system-prompt AGENTS.md` 显式注入 | AGENTS.md 属配置级稳定内容，不破坏 prompt cache，文档 §1.5 的缓存警告不适用 |

**关键约束**：`@file` 在 RPC 模式下被拒绝（`main.ts:638`），因此项目必须把图片经 RPC prompt 的 `images` 字段传给 pi（`runner.ts` 组装 `{type:'prompt', message, images:[{type:'image',data,mimeType}]}`），这是协议决定的路径，不是可选项。

### 2.2 产物：pi 本身没有检测机制

pi 内部**不存在**任何产物检测/捕获逻辑：

- agent 写出的文件只是磁盘文件，模型在正文里用路径引用；
- `read` 工具读到的图片以 base64 内联进工具结果，再进入会话历史（`utils/tool-result-images.ts` 只做缩放归一化，不做去重/入库）。

对照文档 §2.2 的三种方式：pi 原生等于「(b) 模型声明」的弱化版（连 `MEDIA:` 标记都没有，只是正文里裸写路径）。**项目在 pi 之外补上了 (c) 差分检测**——这正是集成做对了的地方。

## 三、项目前后端实际交互（现状梳理）

### 3.1 上传方向（用户 → 模型）

```
前端 PiChatNodeHost（≤4 张 base64 data URL）
  → POST /api/modules/bookplate/chat { message, images, skills, workspace_id }
  → 后端 preparePiWorkspace（AGENTS.md 软链 / skills 装配 / models.json / settings.json）
  → pi RPC 子进程 prompt 命令 images 字段 → user 消息 ImageContent → chat.jsonl
```

- 图片 base64 会**常驻会话历史**（chat.jsonl），会话存续期间每次 provider 请求都会重发（见 §4.4）。
- 前端仅支持「文本 + 图片」；**不存在任意文件上传**（文档 §1 的三类分流只实现了图片一类）。
- 请求体上限已提到 50MB（`server.ts` bodyLimit，适配 base64 膨胀约 33%）。

### 3.2 产物方向（模型 → 用户）

```
每轮开始 snapshotWorkspace(ws)（readdirSync/statSync 全量递归）
  → pi 执行一轮（工具写文件、生图 outputs/、bash 等）
  → 每轮结束再 snapshotWorkspace → diffWorkspace（mtime+size，排除 .agents/.pi/.pi-agent/inputs/AGENTS.md）
  → agent_file SSE 事件（transient，不落库） + .pi-agent/artifacts.jsonl（append-only manifest）
```

- **文件面板**：`GET /chat/files` = 当前快照 ∪ manifest 历史（已删文件保留 `exists=false`）。
- **下载/预览**：`GET /skill-files?path=&workspace_id=` —— 鉴权 + `resolveSkillAbs` 双层白名单（词法 normpath + realpath 穿透，仅放行工作区 / skills / agents 根），流式发送、正确 Content-Type、RFC 5987 文件名。
- **刷新后的消息卡片**（水合 `pi-session-hydrate.ts`）：来自 ① 内联图片块 → 鉴权图片卡；② `write`/`edit` 工具调用参数推导；③ 前端对正文的路径正则提取（`workspaceFiles.ts`，把 `/…/runtime/{uid}/workspace/{wsId}/outputs/x.png` 换算为 skill-files URL）。
- **manifest 只服务于文件面板，不参与按消息水合**——这是 §4.2 要讲的核心缺口。
- FastClaw 模式：从工具结果正则收割路径 → 拷入 `outputs/` → 复用同一套 agent_file 管线（近似文档 (a)）。

### 3.3 存储布局（全部本地磁盘）

```
runtime/{uid}/workspace/{wsId}/       单个 chat 节点工作区（软链装配 + agent 产物）
runtime/.agent/skills/、runtime/.agent/agents/{id}/AGENTS.md
runtime/{uid}/skills/                 用户已安装 skill 登记
```

无对象存储、无 files/artifacts 表；寻址 = `workspace_id + 工作区相对路径`（拼进 URL）。注意 `runtime/` 内含每工作区 API Key（models.json / settings.json / web-search.json），已 gitignore，但需持久卷 + 备份策略。

## 五、优化建议

### 5.1 值得做（当前收益最高）

**① 水合时把 manifest 检测到的产物绑定到消息卡片（补「shell 写文件被漏」缺口）**

- 现状：`bash python make_report.py` 生成的文件（文档 §2.1 的场景）进了 manifest 和文件面板，但**不会出现在聊天消息的文件卡片里**，除非模型恰好在正文写了路径（前端正则）或用了 `write`/`edit`（水合推断）。
- 做法：差分时在 manifest 记录产生该产物的轮次/时间戳（或 diff 时直接写 entry-id），水合时按「上一条消息时间戳之后新增/变更」把 manifest 条目挂到对应 assistant 消息的 `files` 上。
- 涉及：`backend-ts/src/services/pi/snapshot.ts`、`pi-session-hydrate.ts`。
- 验证：刷新后 bash 生成的产物出现在消息卡片（现有 `pi-session-hydrate.test.ts` 可加用例）。

**② 去掉每轮双次同步工作区遍历**

- 现状：`runner.ts` 每轮首尾各一次 `snapshotWorkspace`，内部是 `readdirSync`/`statSync` 全量递归——**同步阻塞后端事件循环**，多租户并发 + 大工作区时影响全服。
- 做法：单次遍历同时产 before/after（首轮浅层采集或首尾合并遍历）；或改异步遍历。
- 说明：`pi-agent-optimization-plan-2026-09-02.md` 的 P3-10 已标记该项但未实施。
- 验证：产物差分行为回归（`pi-agent-run.test.ts` / 手工验证 agent_file 卡片）。

**③ 产品决策：是否支持任意文件上传**

- 现状：聊天只收「文本 + 图片」，文档 §1 的「小文本 / 大文件」两条路没有入口。
- 若产品要支持挂载文档/代码/日志：文档蓝图（先落存储 → file_id → 小文本注入 user 消息 / 大文件落工作区给工具）正好适用，pi 的工具半截（工作区 + read/grep/bash）已就绪，只需补上传与落盘侧。

### 5.2 pi 协议绑定（记录成本，不做对抗性改造）

**④ base64 常驻会话历史导致的 token 成本**

- 用户首轮图片与 `read` 工具读到的图片都会以 base64 存进 chat.jsonl，会话内每轮 provider 请求重发，直到压缩。
- RPC 协议只接受内联 base64 `ImageContent`，无 URL/file_id 附件通道，不改 pi 无法根治。
- 现有缓解：2000×2000 自动缩放 + 每轮 4 张上限。可进一步把聊天附件缩放目标调小（如 1024–1568px），但成本是集成固有的。

### 5.3 暂缓（按需再做）

| 项 | 触发条件 |
| --- | --- |
| 对象存储 + file_id + files/artifacts 表 | 多 worker / HA / 沙箱回收（文档 §2.3 论证即迁移依据）；迁移前至少保证 runtime/ 持久卷 + 备份 |
| `skill-files` 增加 Range / 文本分页 | 工作区出现大日志等大文件 |
| 目录树 + 懒加载 + 虚拟滚动 | 工作区达到代码仓库规模 |

## 六、总结

- 设计文档的原则合理，且与 pi 架构高度一致；项目已落地**文档推荐的核心项**：差分产物检测 (c)、大文件走工具、所有文件端点鉴权 + 路径白名单、服务端会话真相源、流式下载。
- 优化优先级：**① 水合绑定 manifest 产物到消息** > **② 单次/异步工作区遍历** > **③ 文件上传产品决策**。其中 ①② 已实施完成（见第七章），③ 留待产品决策。
- 文档里其余断言（对象存储、file_id 表、目录树、Range 端点）属于「扩展/规模触发项」，不是当前实现的缺陷——不要提前建设。

## 七、优化实施记录（2026-09-04）

> 本段记录 ① ② 两项优化的实际落地：改动文件、实现要点、测试与验证结果。编码原则：KISS、模块化、高内聚低耦合、单文件不过度膨胀。

### 7.1 ② 单次工作区遍历（每轮 2 次全量 walk → 1 次）

**`backend-ts/src/services/pi/snapshot.ts`**

- `walkWorkspace` 现在**直接剪枝差分排除目录**（`.agents/` `.pi/` `.pi-agent/` `inputs/`），不再递归进入最大的几棵树（装配的 skills 软链目标、会话 `chat.jsonl`、产物 manifest、已上传图片）。由于这些路径在 diff 阶段本就被排除，剪枝前后结果完全一致，只是少走了遍历。
- 新增工作区基线：`PI_BASELINE_REL`（`.pi-agent/snapshot.json`）、`readWorkspaceBaseline(ws)`（缺失/损坏 → `null`）、`writeWorkspaceBaseline(ws, stamps)`（best-effort，与 manifest 同风格，失败静默）。

**`backend-ts/src/services/pi/runner.ts`**

- 轮开始：`readWorkspaceBaseline(ws) ?? snapshotWorkspace(ws)` —— 仅首轮或基线缺失时才真遍历，语义与旧「轮首遍历」完全一致。
- 轮结束：一次遍历产出 after，随后 `writeWorkspaceBaseline(ws, after)` 落盘。
- 基线在**磁盘**上，进程被杀/重启后依然存在——重启后既有产物**不会被重复上报为 `agent_file`**（附带修正了旧实现的这一隐性行为）。

### 7.2 ① 水合时把 manifest 产物绑定到消息卡片

**`backend-ts/src/services/pi/snapshot.ts`**

- 新增 `readArtifactManifest(ws)`：容错 JSONL 读取器，`ts` 字段对旧行可缺省；`listWorkspaceArtifacts` 改为复用（删除重复解析）。

**`backend-ts/src/services/pi-session-hydrate.ts`**

- 历史构建完成后，把 manifest 条目绑定到**产生它的那条 assistant 消息**上：manifest `ts`（轮末 diff 时刻）落在该轮 assistant ts 与下一轮 user ts 之间，因此绑定到满足 `ts <= entry.ts` 的最后一条 assistant。
- 仅绑定**当前仍存在**的文件；卡片按路径与 `write`/`edit` 推断卡、内联图片卡**去重**。
- **无需改前端**：水合后的 `files` 直接走既有 DTO 通道渲染。

> 行为说明：同一轮里某文件既被 `write` 又被 diff 检测到时，`write` 卡胜出（保留其 `size: 0`）；仅 manifest 检测到的文件带真实大小。如需在重叠场景下改用 manifest 的真实 size，是一行改动。

### 7.3 测试与验证

- `pi-session-hydrate.test.ts`：+2 用例 —— 多轮绑定 + write 卡去重 + 已删文件跳过；旧版无 `ts` 行不参与绑定（list 合并仍兼容）。
- `pi-agent-run.test.ts`：+1 e2e 用例 —— 第 1 轮生成产物并断言基线文件存在 → 杀进程 → 第 2 轮**不再上报 `agent_file`**（基线跨重启存活）。
- `npx tsc --noEmit` → 0 错误。
- 全量 `tests/api/pi-*` 回归 → **85/85 通过**（含 reuse、SSE wire、widgets、web-access 套件）。

### 7.4 遗留项

- ③ 文件上传产品决策：聊天仍只收「文本 + 图片」，何时支持任意文件上传由产品方向决定（文档蓝图与 pi 工具半截均已就绪）。
- ④ base64 常驻会话历史的 token 成本：RPC 协议绑定，未做对抗性改造。
