# 节点输入接线（连线即输入 · 端口类型匹配 · 占位符模板）

> 本文档描述画板节点「输入/输出」的接线机制（**破坏性更新，不再向后兼容**）：
>
> - **连线即输入**：节点的输入 = 直接连线的上级节点（1 级），不再沿祖先链向上追溯（BFS 已移除）；
> - **端口类型**：每个节点模板声明「输出类型 + 接受的输入类型列表」，连线类型不匹配时给出软提示（红线 + 徽标 + 运行提示）；
> - **图书元数据**：通过节点「运行设置」中的「包含图书元数据」开关（上下文配置）注入，与是否连线无关；
> - **手动运行**：节点默认不自动运行，点击「运行」按钮执行；可逐节点开启「自动运行」；
> - **占位符模板（文本聚合）**：文本输出节点可被 `{占位符}` 引用，按自定义格式拼接多上级文本；
>   **能力由端口类型声明 + 文本字段约定推导，新增文本输出节点类型默认支持，无需改占位符代码**（见 1.7）。

## 1. 核心机制

### 1.1 连线即输入（直接上级，1 级）

`resolveDirectParents(nodeId, nodes, edges)` 只取**直接**连线的上级节点（画线连上即输入），
不再像旧版 `findUpstreamAny` 那样沿整条祖先链向上 BFS 追溯。**所有节点的输入收集统一走
`execution.ts` 的 `collectNodeInputs()`**——按「输出端口类型」把直接上级分组
（`text`（含 `any`）/ `image` / `document`…，端口声明见 1.3），任何节点消费输入都从分组取、
不按节点类型名逐个枚举；`resolveNodeRunInputs()` 在其之上按角色配置表（`TEXT_ROLE`）分桶
（主提示词 / 图片分析 / 普通文本上下文）并合并多个同类上级：

| 节点 | 使用哪些直接上级 | 合并方式 |
|---|---|---|
| 图片分析 | 图片输出上级（`output === image`：`image_upload` / `image_generation`…，参考图）、`book_info`/根节点元数据（封面兜底） | 图片取第一个；封面走 `coverUrl` |
| AI 文本生成（提示词） | `image_analysis`（分析）、文本输出上级（文本上下文）、元数据 | 分析/文本分别合并 |
| 图像生成 | `text_generation`（主提示词，`TEXT_ROLE=prompt`）、`image_analysis`（分析）、文本输出上级（并入提示词上下文）、输出端口类型为 `image` 的上级（`image_upload` / `image_generation`…，图生图参考）、图书封面（`includeBookCover` 图生图参考） | 提示词优先，无则回退元数据文本；分析/文本并入；参考图 = 输出类型为 image 的上级，data URL（图片上传）优先 |
| AI 对话 | 任意直接上级的文本输出（`includeUpstream`）+ 图片输出（`includeUpstreamImages`，图片上传 / 图像生成） | 文本逐节点收集；图片转 data URL 后作为视觉上下文 |
| 文本聚合 | 全部**文本输出**直接上级（按端口类型声明推导） | 模板中 `{别名}` 逐个替换为对应上级文本；结果随上级变化自动重算 |

> - 「文本上下文」收集按端口类型推导（`output ∈ text/any`），**任何文本输出节点**（文本 / AI 对话 /
>   文本聚合 / 未来新增）直接连给 AI 文本生成、图像生成都会自动并入上下文，无需逐个枚举节点类型；
> - 「图生图参考图」同样按端口类型推导（`output === image`，图片上传 / 图像生成…，data URL 优先），
>   未来新增图片输出节点自动生效；
> - **复合输出节点**（模板声明 `output_types`，如「中国传统纹样」同时输出 `image + text`）：
>   文本 / 图片分组按全部输出类型判定，图片消费节点与文本消费节点都能接入，AI 对话可同时取两者
>   （见 1.3）；
> - **新增输出类型（音频 / 视频…）零改动接入**：`collectNodeInputs` 按端口声明自动把对应上级落入
>   `byPortType.audio` 等分组，下游按分组消费即可；输出提取按 `data.xxxUrl` 字段约定补一个提取函数
>   （文本已约定 `data.output/content/analysis`、图片 `data.imageUrl`）。

### 1.2 手动拖线连线（自由搭建）

除「＋」按钮自动连线外，可在画布上**手动拖线**连接任意两个节点：

- 按住源节点**右侧连接点（输出端口）**拖拽 → 出现跟随鼠标的幽灵连线（`ConnectionGhost`）；
- 松手落在目标节点**左侧连接点（输入端口）**或**节点卡片任意位置**上即创建连线（`useManualConnection`）；
- 拖拽中**实时类型匹配着色**：幽灵线命中可匹配目标 → 主色加粗；命中类型不匹配目标 → 红色；
  未悬停到目标 → 弱化中性色（匹配/不匹配一眼可辨，无需等到松手）;
- 全程软校验：**禁止自连 / 重复连线（同 source→target）/ 成环**（会 toast 提示并忽略）；
  端口类型不匹配**不禁止**，连线照建、渲染时标红（与 1.3 软提示一致）；
- 创建前记历史（Ctrl+Z 可撤销）；`Esc` 或空白处松手取消。

实现链路：`CanvasNode` 右锚点 `onPointerDown` → `CanvasContext.onAnchorPointerDown` →
`useManualConnection.onAnchorPointerDown`（登记源节点 + window 监听）→ 指针移动 `elementFromPoint`
检测落点（`[data-anchor-input]` 锚点优先，`[data-node-id]` 整卡兜底）并按 `matchPortType` 实时着色
（幽灵线命令式更新，零 React 渲染）→ 松手校验后 `setEdges`。

### 1.3 端口类型（后端声明，唯一权威）

`backend-ts/src/api/canvas/node-types.ts`（活动后端；对应 Python `backend/app/modules/bookplate/node_types.py`）每个模板声明：

```python
{
    "type": NODE_IMAGE,
    ...
    "output_type": "image",        # 该节点产出什么
    "input_types": ["text", "image"],  # 接受哪些类型的上级输入（空 = 不接受上游）
}
```

端口类型枚举：`text / image / document / audio / video / any`（`any` = 任意类型，预留）。
当前实际使用 `text`（图书元数据 / 文本 / 图片分析 / 提示词生成 / AI 对话 / 文本聚合 / 提示词检索 / 万年历 / 天气）、
`image`（图片上传 / 图像生成 / 纹样 / 检索类节点…）与 `document`（Skill 检索），`audio` / `video`
为未来节点预留。

**复合输出（一个节点同时产出多种类型）**：模板可在 `output_type` 之外再声明 `output_types` 数组，
如「中国传统纹样」`output_type: "image"` + `output_types: ["image", "text"]`——主输出为图片
（连线展示 / 主类型），同时产出详情说明文本。缺省时 `output_types = [output_type]`（单输出节点无需声明）。

前端 `nodeTypes.ts` 的 `NODE_PORT_TYPES` 为**静态镜像**（注册表异步加载期间 + 管理页展示兜底），
注册表到达后以后端权威值覆盖；`matchPortType(source, targetTypes)` 判定：
- **源可为单个类型或复合输出的类型列表**：命中任一目标输入类型即为匹配
  （图片消费节点拿图片，文本消费节点拿文本，AI 对话可同时取两者）；
- `any` 匹配任意；目标输入列表为空 = 不接受任何上游输入；
- 任一侧类型未知返回 `unknown`（不判为不匹配，避免误报）。

### 1.4 类型不匹配 = 软提示（不禁止连线）

| 位置 | 表现 |
|---|---|
| 连线 | 红色虚线（`NodeEdge.compatible=false`） |
| 目标节点标题旁 | 「类型不匹配 ×N」红色徽标（`CanvasNode.mismatchBadge`） |
| 点击「运行」 | toast 明确原因（如「连线「图片上传」类型不匹配，已标红」） |

连线本身仍可建立（保持搭建自由）；不匹配的输入在运行时被忽略并给出提示。

### 1.5 图书元数据：上下文配置（`NodeRunSettings`）

可执行节点（图片分析 / 提示词生成 / 图像生成）的「运行设置」弹层（节点组件右上角 ⚙）：

- **包含图书元数据**（`includeBook`）：开启时无论是否直接连线，都把画布**根** `book_info`
  节点（无入边者优先）的元数据作为上下文注入；直接连线了 `book_info` 时天然生效。
  默认值 = **直接上级是图书元数据才开启**，否则关闭。
- **加载图书封面图片**（`includeBookCover`，图像生成 / 图片分析节点）：开启时注入封面图，
  与图片类上级参考图一并作为**图生图参考**（Agnes 多图合成契约）；穿透/兜底口径与 `includeBook`
  一致（直接连线优先 → 连线上游 → 画布根节点），封面代理抓取失败时自动跳过、不阻断生成。
  默认值跟随 book_info 连通性：显式设置优先；未显式设置时，有实际连通的 book_info
  （直连或连线上游）默认开启，无连通（仅画布根节点兜底）默认关闭，需手动开启。

### 1.6 手动运行

- 新增节点默认不自动执行；
- 每个可执行节点在待运行态提供「运行」按钮（▶）；
- `runNode(node)` 返回**待运行原因字符串**（输入不足 / 类型不匹配 / 图片类上级暂无可用图片等），
  `handleRunFor` 以 toast 提示；执行成功返回空串。

### 1.7 占位符模板（文本聚合 · 公共机制）

「文本聚合」节点用 **模板 + 占位符** 把多个上级文本按自定义格式拼接：

```
## 我是自定义标题

{我是上级节点1的占位符}

---

## 我是另一个自定义标题

{我是上级节点2的占位符}
```

**两处关键推导（新增文本节点零成本接入）：**

1. **谁可以被引用**：占位符能力 = 端口类型声明推导。`isTextOutputNode(node, portTypesOf)`
   判定节点输出的全部类型（`outputs`）含 `text / any` 即认为产出可引用文本——
   **复合输出节点（如纹样节点同时输出 `image + text`）的文本同样可被引用**；
   仅有 `image` 输出的图像生成 / 图片上传不参与。
   因此新增节点只要声明 `output_type: "text"`（复合输出则 `output_types` 含 `text`），
   无需改占位符代码即可被引用。
2. **文本从哪提取**：`nodeTypes.ts` 的 `nodeOutputText()` 有**约定式兜底**——按
   `data.output → data.content → data.analysis` 顺序读取。新增文本节点把对外文本存入任一约定字段
   即自动可读（无需逐个加 case）。

**实现分层（高内聚低耦合，可复用）：**

| 层 | 文件 | 职责 |
|---|---|---|
| 引擎 | `textTemplate.ts` | 占位符解析 / 别名同步 / 渲染；`toPlaceholderSources()` 把上级节点映射为来源行 |
| 公共组件 | `components/PlaceholderPanel.tsx` | 来源行（色点 + 标题 + 可编辑别名 + 插入按钮）+ 未匹配警告，纯展示受控 |
| 节点 | `canvas/nodes/text/TextAggregateNode.tsx` | 模板编辑 / 预览 / 光标插入，编排前两层 |

**运行语义**：纯文本变换、不调 API、无「运行」按钮——输出随上级内容 / 连线变化**自动重算**
（`app/routes/CanvasPage.tsx` 的聚合 effect），下游（AI 文本生成 / 图像生成 / AI 对话 / 其他聚合）直接消费 `data.output`。

> 别名默认取上级节点标题（变体名 / 模板名），同名自动加「· 2」；可在面板内改名，重名会被拒绝。

### 3.2 Handler 注册（v2 重构后）

> 原 `frontend/src/canvas/core/useNodeHandlers.ts`（1472 行）已按「行为族」拆分为独立模块：
> 编辑器 patch 工厂 `canvas/core/editorPatch.ts`、工具类 Fetch 工厂 `canvas/nodes/ai/infra/useToolHandlers.ts`、
> 图片输出工厂 `canvas/core/useImageOutputHandlers.ts`。新增节点类型时**无需复制 handler 骨架**，
> 只需按节点类型匹配以下工厂，一行调用即可。

**编辑器类节点**（写入 `node.data` 的 patch 操作，如知乎 / Wikipedia / 翻译 / 网络搜索 / 地图海报 / 艺术地图 / 图片检索 / 纹样 / 配色 / 邮票）：
```ts
// useNodeHandlers.ts 中：
const editorPatchFns = { nodesRef, recordHistory, updateNodeData };
const handleUpdateMyNodeEditorFor = useEditorPatchHandler(['my_node_type'], editorPatchFns);
```
- `editorPatch.ts` 的 `useEditorPatchHandler` 自动处理：类型白名单检查、变更检测（`patchHasChanged`）、可选撤销历史。
- 新增类似节点只需一行，无需重复 `patchHasChanged` + `recordHistory` 逻辑。

**工具类 Fetch 节点**（调后端 API 查询，如日历 / 天气 / Wikipedia 检索与全文）：
```ts
// useToolHandlers.ts 的 config 区：
const MY_TOOL_CONFIG: SimpleToolConfig<string> = {
  nodeType: 'my_tool',
  endpoint: '/modules/bookplate/my-tool',
  resolveInput: (payload, upstream) => upstream || payload,
  startExtras: (payload) => ({ myField: payload }),
  buildBody: (payload, input) => ({ myField: input }),
  okExtras: (res) => ({ output: res?.output ?? '' }),
  errLabel: '我的工具',
};
// useToolHandlers 中：
const handleFetchMyToolFor = useSimpleToolHandler(ctx, MY_TOOL_CONFIG);
```
- 骨架自动处理：`isGenerating` 防重、输入空检查、`isGenerating`/`error` 状态管理、错误文案统一。

**带 tabData 隔离的 Fetch 节点**（按模式/源隔离结果，如知乎 / 翻译 / 网络搜索）：
```ts
const MY_TABBED_CONFIG: TabbedToolConfig<MyPayload> = {
  nodeType: 'my_tabbed',
  endpoint: '/modules/bookplate/my-tabbed',
  tabKeyField: 'source',
  activeDefault: 'random',
  resolveInput: (payload, upstream) => upstream || payload.query.trim(),
  startTabExtras: (payload) => ({}),
  topExtras: (payload) => ({}),
  buildBody: (payload, input) => ({ query: input, ...payload }),
  okTabExtras: () => ({}),
  outputOf: (res) => res?.output ?? '',
  errLabel: '我的工具',
};
```
- 骨架自动处理：tab 级 `isGenerating` 隔离、`tabData` 更新、激活 tab 切换。

**图片选中保存节点**（选中 → 下载落盘 → 写回 `node.data`，如图片检索 / 艺术检索 / 纹样 / 配色）：

```ts
const MY_SAVE_CONFIG: SelectImageConfig = {

// useImageOutputHandlers 中：
```

**图片导出落盘节点**（导出 PNG → 保存到后端 → 写数据库历史记录，如小票 / 邮票）：
```ts
const handleExportMyImageFor = useImageExportHandler(ctx, {
  nodeType: 'my_image',
```

**简单图片导出节点**（后端已落盘，直接写回 `imageUrl`，如地图海报 / 艺术地图）：

### 3.4 注意事项

- **占位符零成本接入**：文本输出节点只需声明 `output_type: "text"` + 把对外文本存入
  `data.output / content / analysis` 任一字段，即自动获得「被占位符引用 + 并入文本上下文」两种能力；
  复合输出节点（如纹样同时输出图片 + 文本）同理——`output_types` 含 `text` 即默认支持占位符；
- **端口查找**：`PortTypesLookup` 定义在 `canvas/nodes/_shared/nodeTypes.ts`（`canvas/core/execution.ts`
  再导出保持 import 路径），由画布 `portTypesOf` 提供（后端模板声明优先，前端静态镜像兜底）；
- **纯变换节点**（如文本聚合，不调 API）：不提供「运行」按钮，输出由 `app/routes/CanvasPage.tsx`
  的聚合 effect 随上级变化自动重算并写入 `data.output`，无需走 `runNode`；
- **历史记录与快照**：`library/history/useGenerationHistory.ts` 按直接上级组装 stage 结果——若提示词路径
  经聚合节点中转，stage2.prompt 可能为空（边界场景，按需扩展）；连线子图快照恢复见 3.5；
- **`nodeOutputText` 约定**：不要破坏 `output → content → analysis` 的兜底顺序；结构化数据
  （图书元数据 / skill 列表）走类型专属格式化，其余类型一律走约定字段。兜底只读**字符串**字段——
  若某节点把结构化对象存在 `data.output`，文本提取会得到空串，请使用类型专属格式化；
- **特殊语义分桶**：新文本节点默认并入「文本上下文」（无需改动）；若需要**独立语义槽位**（如
  图片分析单独标注为 `## 图片分析`、提示词生成作为主提示词来源），在 `canvas/nodes/_shared/nodeTypes.ts`
  的 `TEXT_ROLE` 配置表中为类型加一行（`analysis` / `prompt`）即可——`resolveNodeRunInputs` 按表分桶，
  无需改执行代码。

### 3.5 画廊/历史「画板」导入：连线子图快照恢复（新增节点注意）

保存生成记录时，`library/history/useGenerationHistory.ts` 沿结果节点**入边向上 BFS** 采集全部上游祖先
（含结果节点自身）生成 `graph_snapshot`（`canvas/core/graphSnapshot.ts` `buildGraphSnapshot`），并经
`canvas/core/graphSnapshotSanitize.ts` 分层清洗后随 `stage_results` 落库。「画板」导入
（`app/routes/CanvasPage.tsx`）**优先**按快照重建整条链路（`canvas/core/graphSnapshotImport.ts`
`hydrateGraphSnapshot`：重映射节点 id、整体平移到画布右侧、与 `seedDataFor()` 默认值合并），
无快照的老记录才回退按 stage1/2/3 拼接 3 个节点。

#### 3.5.1 恢复逻辑类型无关：新增节点自动适用

采集只走边拓扑、清洗/水合都是通用递归，**恢复逻辑本身零改动即可覆盖新节点**。前提是满足既有约定：

1. `frontend/src/shared/types/index.ts` 的 `CanvasNodeType` 联合类型加入新类型——快照节点的 `type`
   字段就是它（同时按 3.1.4 同步 `nodeLayout.ts`）；
2. `canvas/core/seedData.ts` 的 `seedDataFor()` 加分支——水合重建时以 `{...seedData, ...快照data}`
   补足默认字段（缺分支也能水合，只是缺默认值；画布上新节点本身仍需要该分支）；
3. 输出走约定字段（见 1.7 / 3.4）：
   - 文本 → `data.output / content / analysis`：快照原样保留，下游文本上下文 / 占位符自动可读；
   - 图片 → `data.imageUrl`：**静态 URL 进快照；base64 一律丢弃**。设计口径（方案1）是不持久化中间
     结果图、导入后沿「连线即输入」逐个重跑中间节点复现，**因此图片输出节点必须可按上游输入重算出图**
     （确定性处理节点天然满足；被丢弃的根输入 base64 参考图需由复现者另行补图）；
   - 图片输出类新节点接入「保存落库」用 `useImageExportHandler` 一行配置（见 3.2），生成时把对外图
     写入 `data.imageUrl`（与 `nodeOutputImages` 约定、下游消费、快照恢复三方一致）。

#### 3.5.2 快照清洗的通用规则与边界

`graphSnapshotSanitize.ts` 分层清洗规则（对所有节点类型通用）：

| 规则 | 说明 |
|---|---|
| 丢弃瞬态字段 | `isGenerating / error / reasoning`（`DROP_KEYS`） |
| 丢弃 base64 | 一切 `data:` 开头的字符串（含 data URL），包括中间节点图片、data URL 封面等 |
| 截断超长文本 | 单字段 > 20000 字截断 |
| 数组封顶 | 数组 > 200 只保留末尾 |
| `agentSteps` 封顶 | 最多 10 条、单条字段 ≤ 500 字（Agent 类节点通用，无需特判） |
| `chat` 消息兜底 | 只留最后一轮（2 条）作跨用户画廊 / 会话缺失展示（见下） |

按新节点形态需要留意的边界：

- **新增运行态大字段**（如 `isExporting`、搜索 `items` 缓存、`tabData` 等）：通用递归会顺带保存
  （占体积、不破坏恢复）。不想进快照 → 加入文件顶部 `DROP_KEYS`（瞬态字段集）。
- **类 chat 的大会话结构**：恢复策略是「保留 `workspaceId` 作权柄」——全量会话由宿主挂载时按
  `workspaceId` 从服务端 jsonl 水合（LLM/FastClaw → `{ws}/conversation.jsonl`，Skill Agent →
  `.pi-agent/run/chat.jsonl`），内嵌 messages 仅作跨用户画廊 / 会话已删场景的兜底（只留最后一轮）。
  新增带 `messages` 的类 chat 节点若要同款省体积策略，需在 `sanitizeNodeData` 加对应特判；
  不加则通用递归完整保留全部消息，恢复仍可用、只是体积大。
- **可配置节点**：快照记录 `configId / configName`，导入按原配置绑定，无需额外处理。
- **历史文案**：`useGenerationHistory.ts` 的 `promptText` 三元给图片结果节点写提示词标签（默认兜底
  读 `data.prompt / content`）；需要专属标签才加分支——只影响历史记录展示文案，不影响快照恢复。
- **老记录兼容**：`graph_snapshot` 存在时永远优先；无快照才回退三节点拼接。新增节点不改采集/水合
  逻辑即对历史数据向后兼容，无需迁移。
