下面按你的最终选择，整理一版**可直接落地的 ACP + 标准模式集成方案**。

---

## 一、目标与边界

| 项       | 选择                                           |
| -------- | ---------------------------------------------- |
| 接入方式 | ACP（程序化客户端）                            |
| 运行模式 | **标准模式（Standard）固定**，不动态切换       |
| 业务     | 图书馆书目推荐 / 阅读推广多模态素材创作        |
| 隔离     | 按 `userId` 建目录，每次对话再建子目录作 `cwd` |
| 模型     | 支持任意 OpenAI-compatible API（含 DeepSeek）  |
| 后端     | TypeScript Web 服务                            |

标准模式：完整工具集（文件、Shell、搜索、Skills、计划、子 Agent、工作流等），适合「读元数据/图片 → 规划 → 写文案/落盘素材」的日常创作，不做 PTC/极简/创造。

---

## 二、总体架构

```
用户请求
  ↓
你的 TS 后端（鉴权、业务、目录管理）
  ↓
创建工作区：/data/workspaces/{userId}/{conversationId}/
  ↓
ACP Client（@agentclientprotocol/sdk）
  ↓  stdio JSON-RPC
dsh ACP Server（固定 Standard 能力树）
  · llm-pi-ai（OpenAI-compatible + 可选 DeepSeek）
  · 标准工具：读写文件、bash、搜索等
  · sandbox: workspace-write（限制在 cwd）
  · 每 session 独立 cwd
  ↓
产物写回该对话目录
  ↓
后端读取结果 → 返回前端
```

要点：

- 一个 ACP 长连接可开多个 session（官方支持）。
- 每个 session 的 `cwd` = 该次对话的绝对路径目录。
- 模式在 **Server composition 里写死为标准能力**，协议侧不传 `mode`。

---

## 三、目录与隔离

```
/data/workspaces/                          # 可配置根目录
├── {userId}/
│   ├── {conversationId}/                  # = session cwd
│   │   ├── metadata/                      # 图书元数据 JSON 等
│   │   ├── assets/                        # 封面、插图等输入
│   │   └── output/                        # 生成的文案、海报说明、JSON 等
│   └── ...
```

规则：

1. 新对话 → `mkdir` 上述路径（绝对路径）。
2. `session/new` 时传入该绝对路径作为 `cwd`。
3. 沙箱使用 `workspace-write`，Agent 只能动该目录。
4. 校验 `userId` / `conversationId`，禁止路径穿越。

## 四、ACP Server 配置（标准模式 + 多模型）

### 4.1 能力取向

固定为 **Standard 类组合**：

- 文件读写 / 编辑  
- 沙箱内 Shell  
- 检索（若需要可保留）  
- 计划 / Skills（按需）  
- **不**挂 Code/PTC 工具呈现  
- **不**挂创造模式的 Cordis 自省工具  

以官方 `examples/acp-agent` 为底，去掉 code-mode 相关 overlay，补上你的 LLM 与业务人设。

### 4.2 LLM（OpenAI-compatible 默认）

```yaml
# 示意：挂在 ACP composition 中
- id: llm
  name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      openai-compatible:
        displayName: Default Gateway
        api: openai-completions
        baseURL: https://your-gateway.com/v1
        apiKeyEnv: OPENAI_COMPAT_API_KEY
        models:
          - id: your-main-model
            name: Main Model
            contextWindow: 128000
          # 若有视觉模型，声明 input
          # - id: your-vision-model
          #   input: [text, image]
          #   contextWindow: 128000

      # 可选：同时保留 DeepSeek
      deepseek:
        apiKeyEnv: DEEPSEEK_API_KEY
```

ACP 桥接默认模型：

```yaml
- id: acp
  name: '@deepseek-ai/dsh-acp'
  config:
    provider: openai-compatible
    model: your-main-model
```

### 4.3 权限

```bash
export DSH_PERMISSION_MODE=workspace-write
export OPENAI_COMPAT_API_KEY=sk-xxx
# export DEEPSEEK_API_KEY=sk-xxx   # 若用
```

审批：对 `session/request_permission` 在后端做策略（默认 `allow-once` 或白名单工具）。

### 4.4 启动

```bash
# 锁定 dsh 版本后，用你的 composition 启动
export DSH_HOME=/var/dsh-acp-home
export DSH_PERMISSION_MODE=workspace-write
export OPENAI_COMPAT_API_KEY=...

node your-acp-standard-server.js \
  --config /path/to/acp-standard.cordis.yml
# stdout 仅协议；日志走 stderr
```

## 五、后端集成（TS）

### 5.1 依赖

```bash
npm install @agentclientprotocol/sdk
```

### 5.2 核心流程

```ts
// 1. 启动/复用一个 ACP 子进程 + Client 连接
// 2. initialize
// 3. 新对话：
const cwd = path.resolve(WORKSPACE_ROOT, userId, conversationId);
await fs.mkdir(cwd, { recursive: true });
// 可选：写入 metadata/、assets/

const { sessionId } = await client.newSession({
  cwd,
  // mcpServers / additionalDirectories 保持空
});

// 4. 发任务（文本；图片先落盘再在 prompt 里写路径）
await client.prompt({
  sessionId,
  prompt: [
    {
      type: 'text',
      text: `根据 metadata/book.json 与 assets/ 中的图片，创作阅读推广素材，输出到 output/。...`,
    },
  ],
});

// 5. 收集 session/update 中的 agent_message_chunk；结束后读 output/
// 6. cancel / 断连清理映射
```

### 5.3 会话映射

在你自己的 DB 中保存：

```text
conversationId → { userId, cwd, acpSessionId, status }
```

官方 ACP 当前**不支持 resume**；断连后需新开 session，或自己把历史摘要塞进新 prompt。

### 5.4 多模态输入约定（标准 ACP 限制）

官方 ACP 为 baseline 文本，**不传 image 块**。建议：

1. 后端把封面/插图写到 `{cwd}/assets/`  
2. 元数据写到 `{cwd}/metadata/book.json`  
3. prompt 只传文本 + 路径说明，让标准模式里的文件工具去读  
4. 若主模型不识图：用视觉模型先描述，或挂 vision 类工具插件，或后端预识别后把描述写入 prompt  

生图：通过工具调你的 OpenAI-compatible 生图 API，结果写入 `output/`。

## 七、安全与运维清单

| 项   | 做法                                            |
| ---- | ----------------------------------------------- |
| 路径 | 仅允许己方生成的 id；禁止 `..`                  |

| 清理 | 对话结束策略：保留/归档/删除 `cwd`              |
| 配额 | 按 userId 限流、限磁盘、限并发 session          |

## 八、落地步骤（建议顺序）

1. **本地**跑通官方 `demo:acp`，确认 `session/new` + 绝对路径 `cwd`。  
2. 改 composition：标准工具集 + `llm-pi-ai` 指向你的 OpenAI-compatible。  
3. 后端最小 Client：建目录 → `newSession` → `prompt` → 读 `output/`。  
4. 接鉴权与 `userId/conversationId` 目录规则。  
5. 补权限回调、取消、错误与超时。  
6. 再补视觉/生图（预识别或插件）。  
7. 压测并发 session，再决定进程数。

## 核心原则

把「运行模式」当成**部署/路由维度**，不要写进业务硬编码，也不要假设官方 ACP 会支持 `session/new({ mode })`。

```
阶段一：只有 Standard
阶段二：Standard + PTC / 自定义 preset …
```

扩展时只加「另一种 ACP 能力组合 + 路由规则」，业务层（userId 目录、对话、落盘）尽量不动。

---

## 推荐架构：模式 = 后端路由，不是协议字段

```
业务 API（创建对话 / 发消息）
        │
        ▼
┌───────────────────────┐
│  ModeRouter           │  ← 现在永远返回 "standard"
│  conversation.mode    │  ← 可落库，默认 standard
└───────────┬───────────┘
            │
     ┌──────┴──────┐
     ▼             ▼
 ACP-Standard   ACP-PTC（以后再起）
 (进程/连接池)   (进程/连接池)
     │
     └─ session/new(cwd) + prompt
```

| 层级       | 职责                                               |
| ---------- | -------------------------------------------------- |
| 业务库     | `conversation.mode` 字段，默认 `standard`          |
| ModeRouter | `mode → 哪个 ACP 连接/进程`                        |
| ACP 进程   | 每种模式一套 composition（工具集写死在 Server 侧） |
| 工作区     | 仍是 `{userId}/{conversationId}`，与模式无关       |

这样：

- **第一阶段**：只起一个 Standard ACP，Router 恒返回它。  
- **第二阶段**：再起 PTC（或 `library-promo`）进程，Router 按任务/配置分流。  
- 目录、鉴权、产物路径都不用改。

---

## 第一阶段就该预留的接口

**1. 对话创建时带上 mode（可隐藏）**

```ts
// 对外可先不暴露，内部默认 standard
createConversation({
  userId,
  mode?: 'standard' | 'ptc' | 'custom-xxx'  // 默认 'standard'
})
```

库表建议：

```text
conversations(
  id, user_id, cwd, mode,   -- mode 默认 'standard'
  acp_session_id, status, created_at
)
```

**2. ACP 连接按 mode 管理**

```ts
interface AcpPool {
  getClient(mode: AgentMode): Promise<AcpClient>
}

// 阶段一
const pool = {
  standard: createAcpProcess('acp-standard.cordis.yml'),
  // ptc: 以后再加
}
```

**3. composition 文件按模式分文件**

```text
deploy/
  acp-standard.cordis.yml    ← 现在只用这个
  acp-ptc.cordis.yml         ← 预留，先不部署
  acp-library-promo.cordis.yml  ← 可选业务预设
```

## 后续扩展时怎么加模式

| 新模式                     | 做法                                                         |
| -------------------------- | ------------------------------------------------------------ |
| PTC                        | 新 composition（标准工具 + Code 呈现）→ 新进程 → Router 增加 `ptc` |
| 极简                       | 一般业务用不上；若要，同样新进程                             |
| 业务预设（如阅读推广专用） | 更推荐：复制 standard 改人设/工具，而不是死磕官方四模式名    |
| 同进程多 preset            | 官方 ACP 协议本身不传 preset；除非自研桥接或用社区增强 ACP，否则多进程更稳 |

**不要**在阶段一就在协议层赌「以后 session/new 能传 mode」——官方合同目前没有这个字段。

---

## 和业务的配合建议

- **单次创作**（一本书、一套素材）→ 长期默认 `standard`  
- **批量/固定多步流水线** → 以后加 `ptc`，创建对话时选或由任务类型自动选  
- **强业务人设** → 优先做 `library-promo` 这类自定义 preset，挂在 Standard 能力树上，而不是先上创造模式  

创建对话策略示例：

```ts
function resolveMode(task: TaskType): AgentMode {
  if (task === 'batch_pipeline') return 'ptc'      // 阶段二
  return 'standard'                                // 阶段一与默认
}
```

## 阶段一最小实现（保持可扩展）

现在只需要：

1. 只部署 **ACP-Standard** 一套 composition。  
2. 库里有 `mode` 字段，写入恒为 `standard`。  
3. `AcpPool.getClient(mode)` 已存在，内部先只实现 `standard`，未知 mode 直接报错。  
4. 工作区、权限、OpenAI-compatible 模型配置按前一版方案。  

以后加模式时改动面：

- 新增 1 个 composition + 1 个进程  
- Router / Pool 多一个分支  
- 可选：管理端或任务类型映射  

业务 API、目录规则、前端主流程可不动。

---

## 一句话

**阶段一固定标准模式没问题；把 mode 做成「对话属性 + 后端路由到不同 ACP composition」，而不是写死在业务逻辑里。** 这样后续加 PTC 或自定义预设只是加进程和路由，不用推翻 ACP 集成。
